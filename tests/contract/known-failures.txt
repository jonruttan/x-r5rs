# known-failures.txt -- the specs this bundle is known to fail.
#
# One "UNIT: TEST" per line, matching the runner's own `FAIL:` lines verbatim.
# Blank lines and #-comments are ignored.
#
# BY NAME, NOT BY COUNT, and the difference is the whole point.  A budget that
# is only a number is satisfied by fixing one failure and breaking another,
# which is the exact event a ratchet exists to catch.  Names catch it.
#
# THE LIST MAY ONLY SHRINK.  tests/spec-gate.sh is red when a failure appears
# that is not here, AND when a line here starts passing -- the second is a
# fixed test, and leaving it listed would quietly re-authorise the failure
# later.  Neither direction is a nag: both are one edit to this file, and both
# are things you want to be told.
#
# A line here is not a target and not an excuse.  It is debt this bundle is
# known to be carrying, recorded so it cannot grow in silence.

# --- EMPTY, and that is the claim ------------------------------------------
#
# This bundle has no known failures.  The file stays because an empty contract
# is a stronger statement than a missing one: spec-gate.sh is red the moment
# ANY spec fails, with no line here to excuse it.
#
# What used to be here was the ellipsis group -- nine specs, every one of them
# a syntax-rules pattern.  `(a ... b)` read as an improper list terminated by
# the reader's internal pair-dot marker, a raw C satom that segfaulted on
# access, so R5RS's macro layer could not be written at all.
#
# It was recorded here as "not a patch waiting to be applied", on the reading
# that Scheme's lexical rules are a lang's to impose above the engine.  That
# reading was half right.  The engine did not adopt Scheme's rules -- it
# stopped asserting one of its own: the dot had been a token KIND, scored on
# sight beside the brackets, so any token BEGINNING with a dot was taken whole
# as the separator.  x-engine-c v0.1.4 stopped claiming the character, and the
# list reader now recognises the one-character symbol "." where it already
# decides pair-versus-list.  Nothing in this bundle changed.
#
# x-lang v0.8.1 is the release carrying it.  (release-ref: history -- the
# release the engine fix landed in, not this bundle's pairing.)

# --- WHY THE TWO MAIN-ONLY FAILURES ARE NOT LISTED -----------------------
#
# As of 2026-09-06 this bundle fails two specs against x-lang MAIN and none
# against the v0.10.0 it pairs with:
#
#   define-syntax with define: macro expanding to lambda
#   macro-introduced ... (pitfall 3.2, both paths): let-syntax: and leaves
#     nothing behind
#
# Both are the one defect r5rs/scm/macro.scm's define-syntax note describes:
# x-engine-c v0.2.8 (#41) made `def` scope by the live frame, and let-syntax's
# expansion now leaks its `def` to global.  x-lang took the pin in f3698b11.
#
# THEY STAY OFF THIS LIST BECAUSE ONE CONTRACT SERVES BOTH CI LEGS.  The gate
# is red in either direction, so a name listed here must fail on EVERY leg
# that reads the file -- and these two PASS on the pinned leg.  Listing them
# would turn the pinned leg red (recorded-but-passing) to quiet the main leg,
# trading the verdict this bundle actually makes for the early warning it was
# given.  ci.yml already answers this: the main leg is continue-on-error
# precisely so it can be red without being a verdict.  Let it be red.
#
# So this file still claims what it claimed: against the release this bundle
# DECLARES, there are no known failures.  Measured, whole suite, one file per
# process, from source: 667/0 on v0.10.0, 667/2 on main.
